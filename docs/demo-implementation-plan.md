# TalentFlow 稳定闭环 Demo 实施方案

编制日期：2026-10-25；更新日期：2026-10-27。状态：**本地Mock闭环已实现；T11完成解析与确定性评分缺陷的最小修复，221项Python、4项主题及24组回放通过，B05恢复通过，当前50/54通过、4项待正式签收/验证，M5未完成。** 见[实施记录](demo-delivery.md)、[复验报告](demo-benchmark-fix-20261027.md)与[待确认评分规则](demo-scoring-rules-pending.md)。历史18项浏览器检查保留，本轮未重跑浏览器。

本方案以已完成的项目审查、Q1—Q20 产品决策及 2026-10-26 补充要求为依据，目标是让虚构招聘数据能稳定完成“上传 → 程序解析与核对入库 → 岗位匹配 Agent 分析与人工决策 → 测评发放与 HR 记录结论 → 笔试发放与 HR 记录结论 → 面试预约与反馈 → Offer 审批发放与通知 → 候选人接受 → 入职办理 → HR 确认到岗”，并能恢复常见失败。测评、笔试的外部答题链接必填，试卷文件可选且仅供内部留存；邮件只发链接。HR 手动记录通过／不通过／跳过及备注，不接答题、计分、阅卷或成绩回调。入职由 HR 登记，支持需补充、延期和放弃，最后单独确认到岗。

实施方式：**主 Agent 按依赖推进；可重复、规则明确的工作交给脚本；子 Agent 仅在确有独立审查价值时按需启用。**不固定安排多个子 Agent 并行开发。

**阅读约定：**“已确认”指用户已确定的产品行为；下文保留审批时的**实施建议／工程默认值**作为范围基线；实际落地位置、结果和差异见第 11 节及实施记录。主 Agent 在 M0 根据代码落实技术细节，不把常规工程选择反复交回用户确认；若实际发现业务范围冲突或历史数据无法兼容，再说明具体问题。复用的现有文件会明确标注。用户已在后续消息明确授权按方案开发；本轮据此实施。Q1—Q20 在与旧《AI招聘自动化落地方案.md》冲突时优先；本轮不修改原旧方案。开发协作的 Agent 与产品运行时的岗位匹配 Agent 分开记录，不按业务环节数量增加开发子 Agent。

## 1. 已确认范围与成功标准

| 决策 | 已确认行为 | 对实施的直接约束 |
|---|---|---|
| Q1 | 先交付稳定闭环 Demo | 优先修数据正确性、状态恢复和可验证流程，不建设通用 Agent 平台 |
| Q2 | 多选简历，一人一份 | 每份文件独立形成导入项，不拼接不同人的简历 |
| Q3 | 用人工标注验证 AI | 页面能运行、输出有五个分数，不等于 AI 质量合格 |
| Q4 | 姓名、有效手机号、有效邮箱全部必填后入库；预览可补充；文件独立失败 | 缺字段可保存预览，服务端拒绝不完整入库；坏文件不拖垮好文件 |
| Q5 | 标准化姓名＋手机去重候选人；同人同岗位沿用投递并保留新来源；不同岗位独立投递 | 不因重复导入重置面试、Offer 或其他进度；来源必须关联到具体投递 |
| Q6 | 人工确认事实优先；保留原文和修改历史；匹配资料变化使旧评估过期，由 HR 重评 | 重新解析不得覆盖人工字段；评估绑定资料版本和 JD 版本；不自动回退招聘状态 |
| Q7 | 预约过期后，HR 在原轮次重新签发未来时段和链接；旧链接失效；已确认预约不受影响 | 重新签发与下一轮面试是不同操作；已确认记录不能被重签覆盖 |
| Q8 | Mock 全流程和替身的成功、超时、失败、重试为主验收；真实联通另记 | 自动化测试不依赖真实邮件、模型、会议或企业微信服务 |
| Q9 | 12 份虚构简历、2 份固定 JD、待用户确认的标注；不编造事实，引用可定位，人工修正生效；评分按区间和排序验收 | 标注冻结前不能声称 AI 质量验收完成；不要求随机模型分数逐字逐分一致 |
| Q10 | 真实模型失败明确失败并可重试，绝不隐式切 Mock；保留旧评估版本；本地解析和人工修正仍可继续 | Mock 必须显式选择；失败尝试不生成伪成功评分，不覆盖上一版结果 |
| Q11 | Offer 可编辑岗位、薪资／补贴、地点、入职日、有效期；必填完才可审批；支持退回；审批后改条款必须重审 | 审批绑定条款版本，发送内容必须等于已审批版本 |
| Q12 | 共享 Demo 数据、统一 HR 权限；记录真实登录用户；修复 CSRF；细角色后续做 | 本版不做租户隔离或细粒度 RBAC，但不能用固定“管理员”代替实际操作者 |
| Q13 | 解析优先用程序；岗位匹配使用 Agent 分析；其他业务继续评估是否需要 Agent | 解析主链采用文件提取、规则与人工补齐；匹配分析保留证据和 HR 决策。其他业务分工见 3.7 建议，不默认新增自主 Agent |
| Q14 | 测评使用公司已有题目链接；管理试卷上传／删除，并向对应投递者发测评邮件 | 不管理题目内容，不实现答题、计分或阅卷；资源形式按 Q17，不能把邮件成功当作测评完成 |
| Q15 | 笔试与测评采用相同方式 | 复用资源和邮件能力，区分业务类型及发放记录；不建设在线判题或成绩回收平台 |
| Q16 | 入职信息登记、材料核对状态、账号／工位准备、独立 HR 到岗确认；首版记录核对结果和备注 | 扩展现有入职任务；普通事项完成不自动等于到岗；不默认新增材料文件收集或真实账号开通接口 |
| Q17 | 外部答题链接必填，试卷文件可选上传供 HR 内部留存；邮件只发送答题链接 | 文件不作为邮件附件，不提供候选人下载入口；链接与文件分别校验，保存资源版本与原始链接 |
| Q18 | HR 在公司考试平台查看结果后，手动选择通过／不通过／跳过并记录备注 | 仅用人工决定衔接下一阶段；不回收答卷、不计算成绩；发送成功、打开链接或到期不产生考试结论 |
| Q19 | 未使用资源可以删除；已有发放记录的资源停用并保留当时链接、收件人和邮件记录 | 停用后不能新发放；保留历史，不撤回旧邮件、不删除外部平台试卷、不宣称旧外链失效 |
| Q20 | 首版由 HR 维护登记和办理状态，复用个人资料与 Offer 信息，补预计／实际到岗信息；支持需补充、延期、放弃，最后独立确认到岗 | 不新增候选人填表门户；办理状态与到岗事实分开，异常处理保留操作者、时间和备注 |
| 补充 1 | 主 Agent 推进，程序可完成的交给脚本；子 Agent 只用于确需的独立审查 | 取消固定三线并行开发；脚本执行结果可重复，审查发现由主 Agent 核实和修复 |
| 补充 2 | AI 评估与面试之间加入测评、笔试 | 两者是独立业务环节，不能以现有简历 AI 评分替代；资源、发放与人工衔接见 3.6 |
| 补充 3 | Offer 通知后加入入职办理 | 沿用候选人接受后启动办理的已有闭环，扩展现有入职任务；通知成功本身不等于候选人接受或已经入职 |

同时纳入已确认缺口：自动跟进、历史漏斗及今日新增口径、SMTP SSL／绝对链接／失败状态、Docker 配置来源与持久化、DOCX 表格和空文本处理、本地规则结果保留及人工修订、一键测试脚本稳定性。

本轮边界：保留 SQLite、现有 FastAPI 服务和确定性状态流转；使用现有 APScheduler 依赖完成 Demo 定时扫描。不新增 Redis、Celery、通用队列、通用工作流引擎或多租户权限框架。扫描 PDF 的 OCR、招聘平台真实抓取、真实腾讯会议／日历接入不作为本次完成条件；无文本文件应明确提示限制并允许人工补充，不能显示解析成功。

## 2. 当前事实与基线

- 现有主要入口为 `app/main.py`；数据模型、请求模型和状态流转分别在 `app/models.py`、`app/schemas.py`、`app/services/workflow.py`。各服务和模板已经存在，优先局部修复，不全面重写。
- 当前 `CandidateSource.application` 为一对一关系，`Application.source_id` 有唯一约束。只往 `candidate.sources` 加记录不足以实现“同人同岗位多来源”，还会让不同岗位的数据混用。
- 当前导入以岗位标题生成 `source_job_id`。标题相同不证明是同一岗位；方案建议导入优先选择已有 `job_id`，新建岗位单独处理。
- 当前 `init_db()` 只调用 `Base.metadata.create_all()`，不会升级已有表；新增字段、关联或唯一约束必须通过显式迁移完成。
- `extract_text_from_file()` 已有 TXT／MD／文本 PDF／DOCX 提取，`build_rule_parse()` 已能提取联系方式及部分栏目线索；当前导入随后仍调用 `AIService.structure_candidate()`，需要改为程序解析主链。现有规则依赖关键词和栏目匹配，不能承诺完整理解任意版式和经历；规则未识别不等于候选人没有该能力，应保留原文并提示人工核对。
- 本次核对 `app`、`tests`、`scripts`：未发现测评／笔试专用模型、路由或测试；当前评估审核直接通往待面试。新增阶段需要同步处理状态流转、页面、历史兼容和统计，不能只增加两个菜单。
- 入职已有 `OnboardingTask`、`/onboarding` 页面、Offer 接受后建任务和完成任务接口。当前 `confirm_onboarding_task()` 在没有未完成任务时直接推进 `JOINED`，尚没有独立的最终到岗确认操作；不能将这套简版任务直接认定为新增入职办理已完成。
- **此前隔离回归基线为 53 项 Python 测试＋4 项主题测试通过。**这只是先前审查时的结果，不是本轮运行结果，也不覆盖本文新增要求；不能把数量当作未来验收标准。
- 现有工作区有用户未提交修改。实施开始前记录工作区状态，不覆盖、不还原、不清理这些修改；本轮仅更新实施方案和验收清单两份文档。

## 3. 实施前冻结的共同契约

以下为落实已确认业务规则的最小技术方案。M0 阶段由主 Agent 统一模型、接口、服务与模板契约，再按依赖实施。

### 3.1 导入、身份与来源

1. 一次多文件上传返回逐文件结果：成功项含任务标识、文件名、状态；失败项含文件名、错误码和可读原因。建议沿用 `ImportTask`，每个任务只有一份简历，不额外建批次表。每份文件采用独立事务；确认／解析任一项失败不得回滚其他项。
2. 提取正文后先校验空文本，再添加文件名展示信息；DOCX 按文档顺序提取段落和表格单元格；PDF 只承诺有文本层的提取。保留原文件、原文和文本哈希；最小引用使用 `source_id`＋原文片段，定位到所引用来源并展示片段即可，不要求首版建设复杂文档坐标系统。
3. 统一三要素校验函数，覆盖所有新入库入口和 API，预览、确认及候选人修改共用，不能只依赖前端校验。姓名去首尾空白并拒绝占位值；手机先标准化再校验；邮箱做格式校验。**有效邮箱仅指格式合法，不宣称收件箱存在或可送达。**手机范围建议首版沿用中国大陆 11 位手机号并支持 `+86`／`0086` 标准化，属于技术范围建议。
4. 候选人身份键继续使用标准化姓名＋手机号，邮箱不参与身份去重。身份变更若撞到其他候选人，应返回明确冲突，保留当前资料，不自动把两个招聘过程合并。
5. 同一请求重试、同一来源重复确认及并发提交保持幂等，不增加重复来源；新上传保留新来源；新来源但同人同 `job_id` 时沿用投递、增加来源，不重置 `status`、轮次、既有评估或 Offer；不同 `job_id` 建独立投递。仅标题相同不得自动认定为同一岗位。
6. 新简历是新证据，不能绕过人工确认覆盖已有事实。关联来源后，提示 HR 比较和确认差异；已有岗位的 JD 版本不因附件导入静默切换。

### 3.2 事实、人工修订与评估

1. 解析主链使用文件提取＋本地规则＋人工核对，不依赖模型调用。结构化事实以 `candidate`／`chat` 的统一字段为准；`human_summary` 是派生展示，不能成为只影响页面、不影响评分的第二份数据。字段优先级为人工确认值 > 有来源可验证的规则结果；无法确定的字段留待补充，冲突展示给 HR。匹配 Agent 的推断不自动写回已确认事实。
2. 人工修订保存字段路径、前后值、来源、真实用户、时间和递增资料版本。重新解析产生建议，不覆盖已人工确认字段。新文件的原始文本及旧修订记录保留。
3. 岗位匹配输入使用已确认事实、该投递相关原文和指定 JD 版本，并形成不可变输入快照。原文不能只剩规则识别出的关键词，否则会丢失经历证据。原始事实引用 `source_id`＋原文片段；人工确认事实引用修改记录／版本，不能伪装成原文已有内容。不得把候选人的另一岗位聊天／JD 混入当前岗位评估。联系方式在所有匹配模型请求前脱敏；本地解析本身不发在线模型请求。
4. 技能、经历、教育、岗位相关聊天、可到岗信息以及评分所用 JD 变化，属于匹配资料变化；旧结果标记“已过期，待 HR 重评”。只改邮箱／电话格式或内部备注，建议不触发能力评分失效。规则需集中定义，不能由各页面自行判断。
5. 过期只是评估有效性变化，不把已面试、已发 Offer 或已入职的投递改回早期状态。HR 可查看旧版输入与结果并显式重评；失败重试保留上一版结果及其原有过期标记。
6. 匹配分析在显式 Mock 模式正常返回标记为 Mock 的结果；在线模式配置错误、超时、非成功响应、非法 JSON 或结构校验失败，全部记录失败原因并提供重试。匹配失败不影响程序解析和人工补充，页面明确区分本地解析结果与匹配调用状态。首版不保留必经的 LLM 结构化调用；不能在点击重评时偷偷重新调用模型覆盖人工事实。

### 3.3 操作结果、身份和外部副作用

1. 真实登录用户标识由会话读取后向服务传递，不接受客户端任意填写 `actor`。系统定时动作单独标为系统，并记录规则及执行关联；候选人公开链接动作标记对应 Token 身份，不冒充 HR。
2. 各服务返回可区分的成功、Mock、失败结果，HTTP 状态与页面提示一致。建议约定校验错误 422、业务冲突 409、失效链接 410、外部超时／失败使用对应错误分类；具体码值在 M0 冻结。
3. 外部调用使用当前已有同步方式和有限超时，不在持有 SQLite 写锁时等待网络。先记录操作／发送尝试，再调用适配器，最后记录结果并按结果推进业务状态。
4. 只有显式 Mock 成功或真实服务确认成功，才标记对应业务已发送；失败记录保留，不切成 Mock。重试由 HR 触发，已成功记录重复点击不得再次发送。SMTP 超时可能存在“服务器已接收但客户端未知”，应显示待核实，不声称能保证外部邮件恰好发送一次。
5. 公开链接由统一配置的站点基础 URL 生成绝对地址，不依赖用户请求中可伪造的 Host。建议增加配置名 `APP_PUBLIC_BASE_URL`；本地演示可用回环地址，真实收件人联通需另行记录地址可达性。

### 3.4 建议的模型变更与兼容策略

下列新增字段／表名均为建议，实施时由主 Agent 统一修改模型、Schema、迁移和共享读写入口。

| 对象 | 最小建议 | 兼容与约束 |
|---|---|---|
| 导入预览 | 复用 `ImportTask.preview_json` 保存人工修订、字段来源和校验错误；解析运行保留独立输出 | 老的多文件任务不重新拆分写库，标记历史任务并只读展示原记录；新上传严格一文件一任务 |
| 候选人事实 | 增加资料版本；在统一结构化字段保存有效事实和字段来源；修订历史记录到现有审计 | 不用人工摘要替代标准字段；旧记录缺三要素时保留并提示待补，不能删除或伪造补齐 |
| 投递与来源 | 建议增加专用关联表，将 `application_id` 与 `source_id` 关联；一个来源只能归属一个投递 | 保留 `Application.source_id` 作为历史首来源兼容入口并回填关联表；新增来源从新关联读取，避免双向外键循环和跨岗位误用 |
| 投递幂等 | 建议最终增加候选人＋岗位唯一约束 | 先扫描历史重复；存在不同进度的旧重复记录时输出冲突清单，不自动删／并。新写入先执行服务端幂等保护，冲突清理完成后才能建立约束 |
| 评估版本 | 现有 `Evaluation` 保留成功结果，补充资料版本、输入快照、证据引用及过期标记 | 旧评分不重算；无法追溯输入的历史评分标为旧版／证据未完整记录，不能补造 |
| 评估尝试 | 建议增加轻量 `EvaluationAttempt` 保存开始／成功／失败、模型、错误、输入版本和成功结果关联 | 失败不是 0 分；避免为失败结果伪造现有非空分数。该表只是记录调用，不是任务队列 |
| 预约重签 | 复用当前轮次、Token 和失效时间；旧时段标记释放，审计记录重签前后信息 | 事务内替换 Token；已确认预约拒绝重签且保持时段和会议不变 |
| Offer 条款 | 增加结构化薪资／补贴、入职日期、条款版本；复用岗位、地点、有效期字段 | 建议薪资／补贴先用带币种与周期的必填文本，不做薪酬计算器；明确“无补贴”可填 0／无，不能用“待定”冒充完整 |
| Offer 审批 | 审批记录追加条款版本和条款快照，每次审批／退回新增记录 | 不覆盖旧审批；只有当前条款版本获得通过才可发送；历史已发记录保留原文，不伪造审批 |
| 通知尝试 | 复用 `Notification`，增加操作去重标识或使用明确的关联元数据，保存每次结果 | 前端可辨 Mock、成功、失败、结果待核实；不保存密钥和完整认证头 |
| 漏斗历史 | 优先复用 `application.status_changed` 审计事件以及已有评估、面试、Offer 的事实记录 | 只有可证明曾到达的阶段才计入；没有证据的旧历史标注不完整，不能凭当前淘汰状态补造完整路径 |
| 测评／笔试资源与发放 | 建议共用资源及发放记录，用类型区分测评／笔试；保存标题、必填外链、适用岗位、可用状态、资源版本及可选内部文件元数据 | 每次发放绑定投递、资源版本、收件邮箱和通知尝试；不保存题目结构、作答或阅卷成绩；已引用资源只能停用，历史发放快照不受修改影响 |
| 测评／笔试人工结论 | 按投递和阶段保存通过／不通过／跳过、备注、实际 HR 与时间；与发送状态分开 | 审核当前阶段和记录版本；重复提交幂等，旧页面不能覆盖后续进度；不能伪造历史结论 |
| 入职办理 | 优先扩展现有 `OnboardingTask`，覆盖 HR 登记、材料核对、账号／工位准备、延期／放弃和独立到岗确认 | 保留预计／实际到岗信息及变更历史；办理记录与已批准 Offer 快照分开；保留历史已入职事实，不因新增事项倒退旧流程 |

### 3.5 建议接口契约

以下路由仅用于计划中的前后端对接；“新增”不表示当前已存在。主 Agent 在 M0 固定请求／返回模型后再交付模板实现。

| 操作 | 建议接口或现有触点 | 最少请求／响应约定 |
|---|---|---|
| 多文件上传 | 修改现有 `POST /api/import/files` | 返回逐文件 `tasks`／`errors`，单项失败原因不被批次成功消息掩盖 |
| 预览补充 | 新增 `POST /api/import/tasks/{id}/supplement` | 姓名、手机、邮箱、确认事实及预览版本；返回校验错误、更新预览、查重结果 |
| 确认入库 | 修改现有确认接口 | 后端重验三要素与最新预览版本；返回新增／复用候选人和投递、来源标识，不只返回笼统成功 |
| 候选人修订 | 修改现有 supplement／profile 接口 | 统一字段、预期资料版本、修订原因；返回新版本及受影响评估，过时页面提交返回冲突 |
| 解析与评估 | 修改现有 application parse／evaluate 接口 | parse 返回本地解析器版本、缺失与来源，不调用模型；evaluate 使用明确 provider、资料版本、原文与 JD 版本，返回匹配调用状态和历史结果关联，失败可重试 |
| 预约重签 | 新增原 interview 上的 renew 操作 | 未来时段范围／确认动作；返回原轮次的新链接及过期时间；已确认状态拒绝 |
| Offer 编辑／提交／退回 | 在现有 Offer 操作旁补齐接口 | 条款及预期版本；提交完整性检查；审批／退回理由；返回当前版本与有效审批状态 |
| 通知重试 | 新增 notification 或业务对象上的 retry 操作 | 关联原失败尝试，返回新尝试；已成功操作幂等返回原结果 |
| 测评／笔试资源与邮件 | 新增资源维护和按投递发放触点，路由命名在 M0 落定 | 必填链接及可选内部文件、类型与适用岗位；无发放记录时删除，否则停用；选择投递后预览收件人／链接并发送，保留发送快照与失败尝试 |
| 测评／笔试人工结论 | 新增按投递、阶段记录结论的操作 | 当前阶段、预期版本、通过／不通过／跳过、备注；服务端读取实际用户并返回下一阶段；公开候选人无此权限 |
| 入职登记与到岗 | 扩展现有办理操作，新增独立到岗及延期／放弃触点 | 登记与事项状态、预计日期及变更原因；到岗记录实际日期和用户；缺必办项拒绝到岗；放弃后拒绝遗留完成动作 |

### 3.6 Q17—Q20 的实施规则

用户已接受本轮四项建议，grilling 的本轮业务问题已收敛。以下把决定转为实施与验收约定；文件格式、枚举名等属于主 Agent 落地的工程选择，不能标成用户逐项指定。

**资源与发放：**标题、类型、适用岗位及外部答题链接必填；文件可选且仅供已登录 HR 内部留存。邮件正文使用所选资源的外链，不带存档文件。发送前展示候选人、岗位、邮箱、资源和正文；服务端重验资源可用性、类型、岗位及邮箱，并保存不可变的发放快照。链接仅做格式校验，不自动抓取外部题目或验证考试平台内容。

**删除、停用和失败重试：**没有任何发放记录的资源允许删除；一旦建立发放尝试，即使失败或结果未知，也保留资源及快照，只允许停用。停用后拒绝新发放，也拒绝针对它启动新的失败重试；HR 如需发另一资源，必须显式选择并创建新发放，不能暗中替换旧记录。停用不能撤回已经发出或正在发送的邮件。删除／停用与创建发放记录需在事务内检查，避免并发留下失去来源的邮件。

**人工结论与阶段衔接：**发送状态和 HR 结论分开。发送成功只记已发放，HR 从外部平台获知结果后录入结论与备注；不读取答卷或自动拉取分数。按当前阶段处理下表，服务端与页面执行同一约束。

| HR 操作 | 测评阶段结果 | 笔试阶段结果 | 通用约束 |
|---|---|---|---|
| 通过 | 进入笔试待处理 | 进入面试待安排 | 保存用户、时间、备注及依据的发放记录；不由邮件结果自动触发 |
| 跳过 | 进入笔试待处理 | 进入面试待安排 | 未发放也允许跳过；必须写明理由，不能记成考试通过 |
| 不通过 | 终止该投递 | 终止该投递 | 保存原因，不影响同人其他岗位；旧链接／旧请求不能重新推进 |
| 未记录结论 | 保持当前阶段 | 保持当前阶段 | 不凭已发送、打开链接或超时推进；不得直接调用旧排期接口绕过 |

实施时默认“通过／不通过”关联当前阶段已经成功发放或经 HR 核实已发送的记录；没有发放而确需省略环节时使用“跳过”及理由。重复提交原结论返回已有结果；不同结论或旧版本提交返回冲突，不新增回退、重考或改判流程。旧投递已在面试、Offer 或已入职阶段时保留当前阶段，把新增前置环节标为历史未记录；不倒退补发，也不填假通过。

**入职办理：**HR 复用候选人身份和已批准 Offer 信息，登记预计到岗日期、报到信息与备注；材料核对、账号准备、工位准备逐项记录待处理／需补充／已完成、办理人和时间。普通事项全部完成后仍保持待入职，由 HR 独立填写实际到岗日期并确认，才进入已入职。既有个人资料和 Offer 快照不因办理登记被静默改写。

| 办理动作 | 预期状态及后续操作 | 必留证据 |
|---|---|---|
| 标为需补充 | 该事项保持未完成，阻止到岗确认；HR 补充信息后可重新确认 | 原核对结果、补充原因、修改人和时间 |
| 延期 | 更新预计到岗信息并记录原因；继续办理，调整相应提醒，不改已批准 Offer 快照 | 原／新日期、原因、操作者及提醒变更 |
| 放弃入职 | 结束该投递的入职办理，取消未完成事项并关闭相应待办；保留已完成事项和接受 Offer 历史 | 放弃原因、操作者、时间；后续完成／到岗请求被拒绝 |
| 确认到岗 | 登记信息齐全、材料核对／账号／工位均完成才允许；重复确认保留首次事实 | 实际日期、实际 HR、时间及前置事项快照 |

**工程默认值：**首版内部试卷文件支持 PDF／DOCX，大小上限默认 10 MiB 并通过环境配置调整；验证类型、空文件、大小及存储边界，不执行文件内容。外链只接受含主机的 HTTP(S) URL，拒绝脚本／文件协议，保留原始查询参数并安全转义展示。岗位按真实 `job_id` 核对。技术字段、错误码和文件存储路径在 M0 落定，测试必须覆盖上述默认值与配置覆盖；这些是实施选择，不需要再开启一轮产品提问。

### 3.7 产品业务中程序与 Agent 的边界

以下是对 Q13“其他业务再分析”的建议。岗位匹配使用一个职责受限的分析模块即可，先复用现有模型客户端与证据化输出；不因命名 Agent 就引入多 Agent 协商、循环规划或通用框架。具体是否需要只读取证工具，在验证固定输入不足后再决定。

| 业务 | 建议执行方式 | 理由与边界 |
|---|---|---|
| 简历提取、联系方式、已知栏目、格式校验与去重 | 程序＋人工核对 | 输入规则可明确；复杂经历无法可靠归类时保留原文，不把未识别当不存在；不为解析单独调用 Agent |
| 候选人与指定岗位的匹配 | 岗位匹配 Agent＋HR 决策 | 对岗位要求和经历证据做语义比较，给出匹配点、缺口、矛盾、待核实问题和有依据的评分；保留来源及版本，不自动录用／淘汰 |
| 测评／笔试资源管理、选定投递和发送邮件 | 程序＋HR 操作 | 题目和考试由公司外部平台提供；按明确对象和模板发放；不让 Agent 自选收件人、试卷或推断考试完成 |
| 面试时段、冲突、公开预约与轮次推进 | 程序＋人工反馈 | 时区、日历占用与状态都是约束；评价由面试官提供。首版不另加面试 Agent；访谈摘要有实际需求时再评估 |
| Offer 条款、审批、通知与候选人回复 | 程序＋HR 审批 | 条款和发送对象必须确定；模板足以生成正文，Agent 不决定薪资或审批 |
| 待办、提醒、统计、导出 | 定时程序／数据库查询 | 以有证据的状态与时间为依据；无法观察外部考试完成时仅提示 HR 核对，不自动催交或报完成 |
| 入职办理 | 程序＋HR 登记／确认 | 记录事实、验证必办事项和关闭待办；“账号准备完成”是人工确认，不代表系统已实际开通账号 |

匹配 Agent 建议只读使用当前投递资料、关联原文与指定 JD，不读其他候选人的数据，不发邮件、不改招聘状态。程序负责输入脱敏、结构校验、分数范围／加权校验和来源定位；这些校验不能独立证明语义正确，AI 质量仍按人工基准验证。不得把未经核实的模型推断写成已确认的候选人事实。

## 4. 里程碑、任务和退出条件

### M0：共同契约、回归环境与迁移准备

**任务：**记录工作区基线；将已确认 Q1—Q20 映射到模型、接口和阶段约束，落定字段、枚举、错误码及迁移；建立隔离数据库、临时配置及可控时钟；制作旧库迁移样本和备份／恢复流程。主 Agent 统一维护共享文件，将确定性检查纳入脚本，不为并行开发额外设计交接层，也不重复询问已确认的业务问题。

**现有触点：**`app/models.py`、`app/schemas.py`、`app/db.py`、`app/services/workflow.py`、`app/main.py`、`tests/test_services.py`、`tests/test_app.py`。建议新增有版本号的最小迁移脚本及迁移测试，不借机建设通用迁移平台。

**退出条件：**所有新增持久化字段和状态均有迁移／历史数据处理说明；重复投递冲突有可读报告；接口请求、响应、错误和幂等约定一致；空库及代表性旧库可以进入后续实现的测试流程。此阶段不要求 AI 标注已确认。

### M1：导入与人工事实闭环

**任务：**一文件一任务及逐文件事务；DOCX 表格提取和空文本分支；程序解析直接形成预览，移除必经模型结构化；保留规则来源、原文和未知项；预览补充三要素并重查重；同人同岗复用投递并保留新来源；人工修订统一写入事实及审计；匹配资料变更标记评估过期。

**现有触点：**`app/services/imports.py`、`app/services/candidates.py`、`app/ai/service.py`、`app/templates/import.html`、`app/templates/candidate_detail.html`；共享入口由主 Agent 接入。建议新增 `tests/test_import_pipeline.py`、`tests/test_candidate_revisions.py`。

**退出条件：**独立验收清单 B、C 组全部通过；12 份样本可逐份展示和修正；不完整资料无法入库；重复导入不生成重复投递、不回退已有状态；重新解析后人工事实保留且能进入评分输入。

### M2：岗位匹配 Agent、失败语义、证据与标注验收

**任务：**以程序解析和人工确认资料、相关原文、指定 JD 为输入完成岗位匹配分析；按 3.7 建议限制分析职责；去除在线模式隐式 Mock；分开调用尝试和成功结果；保存输入版本／模型／提示词版本；支持重试和旧结果查看；输出证据引用定位；完成 12 份简历×2 JD 的标注草案、评估运行器和差异报告。

**现有触点：**`app/ai/client.py`、`app/ai/service.py`、`app/ai/prompts.py`、`app/services/redaction.py`、`app/templates/evaluations.html`。建议新增 `tests/test_ai_contracts.py`、`samples/ai-evaluation/` 和离线报告脚本。

**退出条件分开记录：**独立验收清单 D 组工程子项通过后，工程契约与 Mock／替身恢复路径可标通过；人工标注经用户确认、固定模型实测并达到冻结门槛后，才能另外标“AI 质量通过”。标注未确认或模型未实测时，质量状态保持待验，不能用 Mock 分数替代。

### M2a：测评资源与邮件发放（Q14 范围已确认）

**任务：**实现测评必填外链、可选内部文件、列表、删除／停用，以及按投递预览和发送邮件；记录资源版本、投递、邮箱、邮件正文与尝试；按 3.6 支持失败重试、停用保护、重复操作和重启恢复；增加 HR 通过／不通过／跳过与备注，衔接笔试。题目设计、作答、计分、阅卷和考试平台接入不在本轮范围。

**触点：**由主 Agent 更新共享模型、状态服务、路由、候选人详情、导航、统计与导出；新增服务和测试文件名在 M0 落定。复用通知适配器、发送失败语义与审计，不新增测评分析 Agent。

**退出条件：**验收 I 组全部通过；内部文件不泄露，收件人与资源选择正确，邮件快照和失败重试可核验；发放状态不冒充考试结果；HR 三种结论及后续阶段符合 3.6。

### M2b：笔试资源与邮件发放（Q15 范围已确认）

**任务：**复用测评资源与邮件能力，用类型区分笔试；实现笔试上传／登记、删除／停用和向对应投递发笔试邮件。测评与笔试的资源选择、模板和发放记录分别可辨，避免误发或互相覆盖；不建设笔试答题、附件交卷、阅卷或代码执行。

## 5. 主 Agent、脚本与独立审查的职责

主 Agent 负责需求梳理、实现、模型／状态／迁移一致性、测试设计及最终集成。按 M0 → M1 → M2 → M2a → M2b → M3 → M3b → M4 → M5 的依赖推进；认证、通知等被前序依赖的基础能力可提前完成，不把里程碑编号当成禁止提前修复的限制。

| 工作 | 默认执行者 | 输出与判断边界 |
|---|---|---|
| 业务代码、数据模型、迁移、页面、状态契约、测试设计 | 主 Agent | 对完整调用链负责，不拆成多个 Agent 争改共享文件 |
| 语法／回归检查、状态转换、幂等、去重、故障注入、重启验证 | 脚本 | 明确输入、期望结果和退出码；不能以脚本能运行替代业务断言 |
| 固定虚构语料、样本清单、结果对比、报告汇总 | 主 Agent 编写后由脚本生成／核对 | 语义覆盖、AI 引用是否支持结论仍需审阅；程序不能自批人工标注；考试题目不属于本系统管理范围 |
| 文件解析、资源管理、时效检查、发放记录、提醒和统计 | 产品内确定性程序 | 与开发验收脚本分开；程序管理测评／笔试发放，不推断外部考试完成或成绩 |
| 跨阶段遗漏、迁移兼容、权限边界的第二视角 | 必要时一个只读子 Agent | 明确审查对象和问题，提供文件位置、复现／反例及影响；不能只输出无证据的风险清单 |
| 产品取舍、人工标注、流程推进和到岗事实 | 用户／指定 HR，主 Agent 辅助 | 子 Agent 和脚本都不能代替业务确认；公司考试的阅卷不在本系统实现 |

子 Agent 不是每个里程碑的必选门槛。仅在主 Agent 有具体理由认为需要独立判断时启用，例如共享状态变更可能影响多个已完成阶段、迁移存在难以证明的历史兼容问题、测试与实现可能共同遗漏同一种边界。调用前说明要检查什么、现有程序证据为何不足；默认一次一项只读审查。运行测试、批量生成样例和整理报告不单独分配子 Agent。

审查结束后由主 Agent 核实发现、补充能稳定复现问题的测试并修复；审查者不直接修改业务代码，也不自行扩展需求。审查意见与脚本结果分别记录，未使用子 Agent 不构成验收缺项。产品运行时的岗位匹配 Agent 是业务能力，边界见 3.7，不混用这套开发分工。

## 6. 数据迁移、备份与回滚

1. **先备份再迁移。**记录当前代码状态和数据库路径，暂停写入；使用 SQLite 备份 API 或停服后一致备份，若启用 WAL 不能只复制主库文件；同时备份上传原文和可写运行配置。备份放在明确专用目录，记录时间、哈希、Schema 版本和恢复命令，密钥不输出到日志或提交仓库。
2. 迁移先在备份副本运行：检测当前表／版本、补充字段和关联表、回填可确定关联，再核验行数、外键及代表性业务记录。迁移可重入并避免重复插入；不会把 `create_all()` 当成升级脚本。
3. 历史重复候选人／投递、同一来源归属冲突、缺少三要素、未知历史阶段单列报告。缺三要素记录继续保留供 HR 补充；不伪造邮箱、不批量清空数据、不猜测合并已有面试／Offer。只有冲突处理完成才增加可能失败的唯一约束。
4. 历史成功评估、审批、已发送通知及确认预约保持原样；缺失版本证据明确标记历史未知。新约束从新写入和明确编辑开始执行，不能静默把旧业务全部判失败或重置进度。
5. 升级失败立即停止后续写入。验证恢复备份可启动且候选人、投递、来源、评估、预约、Offer 数量一致后再恢复服务；不得在失败库上连续尝试不可逆手工修补。回滚恢复旧代码与匹配的数据库／运行配置，保留失败副本用于排查。

## 8. AI 标注集与验收方法

固定语料建议组织为 `R01`—`R12` 和 `JD-A`／`JD-B`，全部显著标为虚构，不使用真实求职者资料。JD 正文和版本哈希在首次评估前冻结；同一候选人对两个 JD 都评估，共 24 个配对。这是小型回归集，不构成统计性的模型效果证明。以下为样本分工建议，不是已经存在或已通过的文件。

| 样本 | 应覆盖的重点 |
|---|---|
| R01—R02 | 对两个 JD 分别有较强且明确证据的匹配样本，形成可解释的排序锚点 |
| R03—R04 | 中等匹配、可迁移技能和一项明确缺口，防止只凭关键词满分 |
| R05—R06 | 关键词出现但项目证据弱，及经历充分但岗位方向不同 |
| R07 | 缺手机号的原始版本，经人工补充后形成可入库与评分版本 |
| R08 | 缺／错误邮箱的原始版本，经修正后复用同一人的核验资料 |
| R09 | DOCX 表格承载关键经历和联系方式 |
| R10 | 多页有文本 PDF，证据分散但能通过来源和原文片段定位 |
| R11 | 首行姓名无标签、规则缺字段或栏目归类冲突，验证原文保留、待补提示与人工优先 |
| R12 | 人工修正一条会影响匹配的错误事实，验证旧评估过期和新版证据 |

损坏文件、空白 PDF、格式非法等作为上述语料的派生负例，不靠增加重复正常简历凑 12 份。缺三要素的原始版本用于导入拒绝测试；质量评估使用其已核验修订版本并保留对应关系。

每份标注包含：文件哈希、原文位置、候选人身份事实、技能／经历／教育、明确未知项、人工修订值与理由、每个 JD 的各维证据／缺口、允许分数区间、必须成立的成对排序和标注状态。先由开发方生成草案，保留“待用户确认”；用户确认后冻结版本，后续调整留版本记录，不能为了让当前模型通过而静默移动门槛。

工程硬门槛：无凭空新增的候选人事实；引用可定位并支持对应判断；未知不写成事实；人工修正真正进入输入；结果包含使用的资料／JD／模型／提示词版本。建议在标注中预先列出关键事实和必须成立的排序，按“关键事实与引用逐项正确＋预设分数区间与排序”验收。具体区间、容忍度及重复运行次数属于标注草案内容，确认前不宣称已批准。

报告分三块：确定性工程契约、显式 Mock 行为、指定真实模型质量。真实模型未运行时显示“未执行”，不填估计分、不用替身结果代替。真实接口联通通过只证明能调用，也不等于语义质量通过。Docker 沿用 README 中的可选部署方式：本地工程验收与容器运行验证分别记录；无 Docker 环境可写未验证，仅静态检查配置不能替代重启／重建测试。

## 9. 运行实现的最小建议

- **自动跟进：**复用已安装的 APScheduler 和 `scan_followups()`。建议单进程 Demo 每 15 分钟运行一次，周期可配置，启动／关闭跟随应用生命周期，`max_instances=1`，每次扫描用独立数据库会话。专项测试注入时间验证规则，集成测试必须实际触发应用调度入口，不能只证明函数可调用。将当前枚举状态转换成规则使用的值，持久化任务后再发内部提醒；需要联系候选人时生成待 HR 确认的草稿。业务条件消失后关闭旧待办，Offer／入职提醒与通用扫描只保留一个调度入口。多进程部署不在本版承诺内。
- **漏斗：**复用现有状态审计，统计每个投递曾到达的阶段而非只看当前状态；当前分布另算。“今日新增”建议明确命名为“今日新增投递”，按创建时间转换为 `Asia/Shanghai` 的日期范围统计；同人新岗位可新增，同岗位新来源不新增。历史不完整单独标注，不从未知状态推演。
- **配置：**建议把页面可编辑配置写入已挂载数据目录下的运行配置文件，首启从环境导入，之后运行配置对这些可编辑键优先；页面和模型／通知客户端必须调用同一个配置读取函数。部署固定值与可编辑值分开列明，保存模型设置不得清空 SMTP／Webhook 设置。含密钥的运行文件必须被 Git 和镜像构建排除，不能仅依赖现有只忽略根 `.env` 的规则。这个优先级是方案建议，实施时在 M0 固定，并迁移既有 `.env` 设置；不能让页面显示一套、容器环境运行另一套。
- **测试脚本：**优先解析实际 Python 解释器，保留 conda 和当前 Python 回退；每次使用新的可写临时根，临时 DB／配置／上传／输出均在其下。语法检查避免向用户已有 `__pycache__` 写入；pytest 与 Node 主题测试失败应透传退出码。不递归删除既有 `output`、缓存或数据目录来绕过 ACL。
- **界面：**延续现有页面和组件，补齐缺字段编辑、失败重试、过期标记、条款审批状态和真实操作者；关键动作显示处理中并阻止重复提交。页面提示和服务端结果必须一致，不能用 Toast 成功掩盖持久化失败。

实际采用 candidate/application JSON 保存人工修订和入职登记；考试只有资源和发放记录两个新业务实体，通知尝试复用 Notification。资源为不可原位编辑的版本；表单 request_key 用于登记幂等。已引用资源停用后，HR 可登记新资源并重新预览，旧快照不覆盖。数据库补列时保留未知历史，不伪造考试结论。

API 统一返回可显示的业务错误：文件/字段非法通常 422，阶段/版本冲突通常 409；身份/会话/CSRF 拒绝为 401/403。收件人修订后不能向旧快照重试。SMTP 未知记录核实为送达时仅补记历史事实；即使原 Offer 已过期，也不重发或允许过期接受。

本轮固定样本的具体分工与早期建议编号有所调整：r09 为表格 DOCX，r10 为两页文本 PDF，r09/r10/r11 分别缺邮箱/手机/姓名并带虚构人工补充值；无标签姓名、人工修正和过期重评等由专项测试覆盖。实际样本以 `tests/fixtures/demo/annotations.json` 和 manifest 为准；不将这些编号调整解释为质量已确认。
