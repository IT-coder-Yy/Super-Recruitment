# 待确认的正式评分规则

日期：2026-10-27。**本轮已修复可确定的解析错误和Mock计数加分问题；下列是招聘评分政策，不由修复代码自动批准。** 原24组草案、审核人和冻结摘要未改。正式基准D01、语义验收D02仍待确认。

| 编号 | 需要确认的规则 | 建议 | 当前实现边界 |
|---|---|---|---|
| R1 | JD缺少业务领域，或某维度缺证，如何处理总分与权重？ | 显示“未知”和证据覆盖情况；JD本身不适用的维度与候选人缺证分开处理。是否剔除维度并重新分配权重，应在基准中统一约定 | 沿用现有35/25/20/10/10权重和缺证0规则，未重新分配。0是缺证占位，不代表能力为0；无领域证据时理论上限90 |
| R2 | 课程、个人项目能否计入20%的“实习/工作相关度”？ | 以相关实践和本人贡献评价，不把企业实习经历设为JD未写明的硬门槛；若改为“相关实践”，须明确与项目维度评价点的区别，避免重复奖励 | 课程项目保留在项目字段，不虚构成实习/工作；Mock仅计算对应字段的明确技术词覆盖，不评价经历深度 |
| R3 | 指定技术栈、可迁移技术、测试与本人贡献怎样给分？ | 逐项区分“技能自述、本人实现、可复验成果”；Java事务经验可作为迁移证据，但不能说已经使用FastAPI。JD明确要求的测试、移动适配、键盘无障碍不能只因词表未识别就忽略 | Mock只覆盖已识别技术词，完整JD原句列为待核对；不声称词项100分等于全部要求符合。具体层级分值仍需用24组样本校准 |
| R4 | 每周可用天数属于资格核验还是10%的意向评分？简历自述是否足够？ | 将可用性单列核验，区分“自述满足、已核实、未知、明确冲突”；未知先追问，不自动拒绝。是否继续计入总分需要确认 | 为复演暂用明确出勤覆盖的0/100占位值；只识别明确每周N天，简历自述标“未核实”，HR提问和不确定承诺不计；不触发招聘决策 |
| R5 | 分数区间、接近样本的排序及通过阈值如何确定？ | 先确认R1—R4，再校准24组分维度证据与允许区间；允许同档或暂不比较。总分供HR参考，不设置自动录用/淘汰阈值 | 原区间不按Mock输出倒改；两条明显强弱排序仅作回归观察，未批准正式区间或完整排序 |

本轮无需确认的确定性修复：JavaScript不等于Java；“未使用FastAPI”不能变成正向技能；“无实习”和“四天意向”不是实习经历；同一项目重复出现不能增加分数；HR的问句不是候选人的承诺。这些已落地并验证。

目前Mock尚不能表达语义质量，例如r09后端的API/事务边界证据没有直接写出项目所用技术词，覆盖分仍可能低于r04；r02/r10/r12前端也可能同分。它们是正式评分待校准的证据，不应通过修改草案隐藏。详见[修复复验报告](demo-benchmark-fix-20261027.md)。

确认后记录规则版本、审核人和时间，再修订基准并开展D02；真实模型D04和真实外部联通H04仍需使用单独批准的测试范围。本轮未调用真实模型、未发送真实通知。
